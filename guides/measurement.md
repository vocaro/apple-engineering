# Measurement

These mechanisms and lessons apply when the stated capability is present. Original
measurements establish their recorded platform and workload; they do not establish
universal behavior on later operating systems or in a different application.

Run whole-machine measurements as exclusive work through heavy-work admission, for example a
lane with `"resource": "exclusive"` started by `python3 scripts/eng run LANE`; see
[shared host](shared-host.md). Measuring on a host that is building something else gives worse
data than not measuring. Budgets stay local and platform-specific. Evidence handling is in
[evidence](evidence.md).

## Fresh-process memory metrics

Measure each input in a fresh child process. Keep these metrics distinct and name which one a
record holds:

- **Peak RSS** from the measured child's `wait4` resource usage. It excludes the parent, the
  build, other checks and earlier children, and as a kernel high-water mark it catches spikes
  between samples. It counts resident shared mappings.
- **Lifetime footprint**, `ri_lifetime_max_phys_footprint` from `proc_pid_rusage`: the kernel's
  high-water mark of the footprint ledger. Read it once more from the exited process before
  `wait4` reaps it, and record whether that read succeeded. A reading taken while the process
  ran misses whatever came later and is only a lower bound for a short run.
- **Sampled footprint**, from periodic samples (for example every 100 ms) recorded with the
  progress stage. It shows where memory went and misses short spikes.
- **`/usr/bin/time -l`**, which prints both a maximum resident set size and a peak memory
  footprint for its child. Label which of its numbers a record uses.

On macOS, `getrusage(RUSAGE_SELF).ru_maxrss` reports bytes.

Gate one metric and record the others as corroboration. Footprint is not simply a steadier RSS.
On an 18-core macOS 27 Mac, across 535 receipts that recorded both (September 2026), footprint
fell further than RSS under warning pressure, was noisier at normal pressure (median spread 0.8%
against 0.2%) and ran from 0.30 to 1.90 times peak RSS depending on the input. Change a gate's
metric only with paired evidence that the new one holds under the conditions that spoil the old
one, and with new budgets measured in it.

OS and framework versions, hardware and build configuration all change memory. Desktop RSS is
not a mobile budget: establish device baselines separately before claiming a device limit.
System services such as OCR can use memory outside the measured process.

A memory ceiling is a regression gate, not an allocation limiter. Give each run a new output
directory and keep its outputs, report and memory trace when a ceiling is exceeded or left
unmeasured. Forced termination can leave staging behind that cooperative cancellation would have
removed.

Test the instrumentation itself: real child allocations above and below a ceiling, isolation
from an earlier child's high-water mark, a footprint peak reached after the last sample, each
pressure outcome, the settle-and-retry and a host that never settles.

To measure a third-party component's cost, run one child per input that reports its own
`ru_maxrss` and monotonic duration, and have the parent cap RSS, CPU and wall time and stop only
its own child. Screen the exact generated bytes with the product's own refusal checks first.
Record cap hits apart from completed measurements, and do not treat the results as thresholds.

Evidence: [PDFReflowLib measurements/footprint-against-rss/record.md](https://github.com/vocaro/PDFReflowLib/blob/dc89a4eccecb99943661709887fd2a61a1a51b29/measurements/footprint-against-rss/record.md).

## Host pressure and unmeasured ceilings

Memory pressure makes macOS compress and page out resident memory, which can only lower a peak.
Sample `kern.memorystatus_vm_pressure_level` while the measured process runs (1 is normal);
readings from before it started do not count. Report one of three outcomes:

- **exceeded**: the peak is above the ceiling. Pressure cannot explain it away; exit 1.
- **passed**: the peak is within the ceiling and pressure stayed normal throughout.
- **unmeasured**: the peak is within the ceiling but pressure rose. It neither passes nor fails;
  exit 3, so that a loaded host is not investigated as a regression.

Before each attempt, wait up to a settle time for pressure to return to normal. Spend a second
attempt on a spoiled measurement only after the host settles, so a host that stays loaded costs
one attempt. Keep every attempt's measurements and samples. An unmeasured ceiling is still not a
pass, and no lane goes green because the machine was busy.

State what the gate cannot see. Run-to-run framework variance bounds the smallest detectable
regression: one OCR-heavy input's peak RSS moved by 50 to 135 MiB between runs of one binary on
one host (macOS 27, September 2026). A ceiling set above that spread catches a return to a large
regression, not a creep of a few percent.

A passed result means pressure stayed normal, not that nothing lowered the peak. A busy host can
move either metric further than that spread without pressure leaving normal, and several runs of
the same input at once read lower than serial runs. Different inputs in separate processes do
not share a reading.

Rerun an unmeasured case alone through the same runner. When another session keeps pressure up,
wait until the level reads 1 for three minutes in a row, then rerun with one job, more attempts
and a longer settle time.

```sh
sysctl -n kern.memorystatus_vm_pressure_level
```

Evidence: [PDFReflowLib measurements/memory-pressure-false-failures/record.md](https://github.com/vocaro/PDFReflowLib/blob/dc89a4eccecb99943661709887fd2a61a1a51b29/measurements/memory-pressure-false-failures/record.md).

## CPU, scheduling and core-wait time

Use thread CPU time for synchronous performance assertions: it excludes scheduling delay and
keeps the work bound. Give asynchronous readiness waits wall-clock deadlines; simulator startup
and UI event delivery can stall under saturation.

Record host activity beside results as context, not as a threshold: idle CPU from the last
`CPU usage` line of `top -l 2 -n 0 -s 2` and load from `sysctl -n vm.loadavg`. Host activity
alone does not invalidate a passing run. Rerun a reproducible load-related failure when
contention subsides rather than waiting for a fixed idle share before starting, and never weaken
an assertion to hide load.

Hold a time limit against the seconds a run took less the seconds its threads were ready and
waiting for a core. `proc_pid_rusage`'s `ri_runnable_time` less the process's CPU time is that
wait. On macOS 27.0 (October 2026), a child that worked for 3 s and then slept read 2.96 CPU
seconds and 3.02 runnable seconds: the runnable clock stood still while it slept. On a quiet
host the limit is the wall clock, so a hung, sleeping or overlong run is still stopped. Add a
wall-clock backstop, for example four times the limit, that bounds the run whatever the host
does. Report one of three outcomes:

- **exceeded**: stopped at the limit with normal memory pressure; exit 1.
- **unmeasured**: stopped at the backstop while still inside its own limit, or stopped at the
  limit under memory pressure, because a thread waiting for its own pages is not runnable and no
  clock separates that wait from work; exit 3. Rerun it on a quiet host.
- **passed**: the run ended on its own.

A higher limit only moves the false failure to a higher load, and a CPU-seconds limit never
stops a blocked run while CPU seconds also grow under load. The clocks sum a process's threads,
so concurrent waits are each counted and the seconds held against the limit can fall below the
CPU seconds. That leniency toward a multithreaded run on a loaded host is bounded by the
backstop. Record the core-wait seconds in every receipt.

## Counting work instead of time

Pin an algorithm's cost by counting the questions it asks, never the seconds it takes. A rule
asked again inside a loop over a page's lines or rows costs the square of the page and changes
no output, so no other gate sees it.

- Bind a tally to the measured task as a task-local value, with one count per kind of question;
  the production path pays one task-local read when no tally is bound.
- A count is the same on a loaded host as on a quiet one and in debug as in release, and it
  stays the test's own however many suites run beside it.
- Bound a count by the input's own sizes, so many askings per line or per rule, with room for
  one more build of the page. Never bound it by the figure a run printed: other rules change how
  often work is rebuilt.
- To pin another rule, add its kind and count it where the question is asked.

## Repeated-process checks

A fresh process measures one input's peak. A long-lived process accumulates what frameworks
retain across inputs, and only repeated work in one process shows that. Run the public API over
several inputs several times in one process, with packaging pinned, and print after each round
the footprint, peak RSS, the default malloc zone and, on the Mac, a `leaks` count; run the same
harness in a simulator for iOS. Footprint after a run swings with allocator reclaim, so bound
growth by the leak count and the default zone. Parallel test suites cannot measure memory.

## Leak investigation

- Build a standalone probe that imports only Apple SDKs, opens each input in an autorelease pool
  and discards every extracted object. Run each mode, such as plain text against rich text or
  per-line against per-page reads, in its own process.
- Inspect allocations with stack logging, only on a process you started:

  ```sh
  MallocStackLogging=1 leaks --atExit -- PROBE INPUT MODE 1
  ```

- A temporary debug-signed probe may need `com.apple.security.get-task-allow`; that entitlement
  never ships. If a password dialog appears, stop and leave it for the owner.
- Stack logging changes memory and timing, so those runs diagnose ownership and never set
  baselines.
- A growing footprint alone does not prove a leak. Compare plain and rich modes, object
  lifetimes and unreachable allocations before attributing a defect to a framework. A submitted
  Feedback report is not a confirmed diagnosis.

## Bounded reruns and campaigns

Decide retry bounds before running. A rerun gets fresh log and result paths and keeps the
earlier attempt. Retry after a confirmed transport failure, not after a failed assertion, and
never weaken an assertion so that a rerun passes.

A concurrency campaign compares the main thread, one background thread and several threads
started together; no framework object crosses threads, and each iteration opens its own input in
its own autorelease pool. Include an SDK-only control without the library, which can
deliberately reproduce a framework abort.

- Keep every child's exit code, output, input, producer and binary identity and trial result.
- Never retry a failed trial.
- On timeout, kill and reap the child's process group.
- Fail a zero exit that lacks a complete, matching positive-control receipt.

A finite passing campaign is bounded evidence, not proof that concurrent use is safe.

## Baselines and builds

Capture a shared baseline once, on a quiet host and with the capability probe, before parallel
work starts. A baseline whose ceilings were unmeasured is no baseline for those ceilings. Build
the baseline's release product once and give every comparison that binary.

Measure release builds. A debug build runs unoptimized and differently: one scanned-book
conversion took 443.5 s in debug against 47.0 s in release (macOS 27, October 2026). When a
device timing run needs debug-only hooks, build Debug with the settings
`SWIFT_OPTIMIZATION_LEVEL=-O SWIFT_COMPILATION_MODE=wholemodule GCC_OPTIMIZATION_LEVEL=s`
through heavy-work admission.

Budget warm-up apart from throughput in any timing that includes it. A framework's first request
in a process, or under a new executable name, can include a model compile or load; the observed
costs are in [shared host](shared-host.md) and
[framework execution identity](../knowledge/apple/framework-execution-identity.md).

## Quality changes and model evaluation

A quality change needs a measurement, not a demo. Measure the configuration the product ships,
at its retrieval depth, path and tier, and pin the exact input the runtime sends: "concatenate
the transcript" can name two different strings. Use multi-trial results with coverage beside
every rate, and capture the output text before diagnosing.

Bars, tiers and OS drift are in [OS and model drift](os-drift.md). Deterministic stages,
positive controls, paired comparisons, clustering, denominators, fitted bars and call plans are
in [model evaluation](model-evaluation.md). Record a rejected approach in the ruled-out register
described in [maintenance](maintenance.md).
